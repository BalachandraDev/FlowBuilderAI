# FlowCapture web app

One web app for everybody: open a link on a phone or a computer, sign in, and turn a conversation into a workflow diagram and an implementation guide (PDF). It installs on a phone like an app ("Add to Home screen"). It replaces the earlier Android/Windows app and Blazor web host, which are kept in `archive/blazor-and-maui/` (see `docs/00-assumptions-and-decisions.md`).

## 1. Two kinds of login

| | Administrator | User |
|---|---|---|
| Makes users, stops access, makes a new password | Yes | No |
| Sets up the free AI key and chooses the AI service | Yes | No |
| Sees every project and the totals | Yes | No |
| Makes projects, adds notes (typed, photographed, spoken), analyses, makes the guide | Yes | Yes, in their own projects |
| Changes their own password (account menu, **Change password**; an **eye** beside each box shows what was typed, so it can be checked, and hides it again) | Yes | Yes |
| Creates, renames and stops modules (Admin, **Modules**) | Yes | No (picks from the list) |
| Deletes a user | Yes | **No** |
| Makes clients and assigns users to them | Yes | No |
| Reads and downloads the documents of **their clients'** projects (an administrator: every document) | Yes | Yes |
| Sees another client's projects | Yes | **No** |
| Changes or deletes a project somebody else started | Yes | **No** (a colleague on the same client can add notes and make documents in it, but only the project's lead or an administrator changes or deletes it) |

**Passwords and deleting users.** Everybody, administrator or user, changes their own password from the account menu (**Change password**): the current password is asked for again, the new one needs at least 10 characters with letters and digits and must differ, and every other phone or browser signed in as that person is signed out while this one stays signed in. An administrator can also give anyone a new temporary password (**Users → New password**). Only an administrator can **Delete** a user (never their own account, and never the last administrator). A deleted user is signed out everywhere, cannot sign in, leaves the users list and every client, and their email can be used again; nothing is erased, so the name stays on the notes and documents they made and the projects they started stay (visible to administrators and to the colleagues on that client). The row stays in the `Users` table with `DeletedAt` set and the email prefixed `deleted-...`; to bring one back, an administrator clears `DeletedAt`, restores the email and sets `IsActive`.

**Clients.** The company works for several customers (hospitals or hospital groups), and a user may handle several of them. An administrator makes the clients in **Clients** (name, place) and ticks the users who work for each (**People**). A user starting a project picks one of their clients (when they have only one it is filled in; with none, the page says to ask an administrator). The structure is **Client > Project > Module > NR/CR > document**. Everybody assigned to a client sees all projects of that client, grouped by client on their home page, with the rights of a *Collaborator*: they add notes, pictures and make documents in any module, and can change or delete only their own notes. The project's starter stays its lead. Assigning someone later gives them the client's existing projects; removing them takes those away (a project they lead stays theirs). **Stop** hides a client from the list users choose from; its projects and documents stay. The access is stored as ordinary project memberships (role `Collaborator`), so the sign-in token and every other check work unchanged; the page asks for a fresh sign-in token when it opens a project the person was assigned to after signing in. Projects made before clients existed were filed, when the app was upgraded, under a client of the same name as the project, with the people on them assigned to it; an administrator can rename, merge (assign the same people) and tidy these. The library, document downloads and diagrams follow the same rule: only the people who can open the project can read its documents.

**Database (administrator).** **Database** in the admin menu shows which SQL Server the app uses and moves it to another one: enter the server address (for example `4.213.114.123,59387`), the database name, and a user and password (or tick *Use the Windows account the app runs as* for a server inside the hospital network), then **Test the connection**. The test changes nothing: it says whether the server answers, whether the database exists, and which tables exist and which would be made. **Make the tables and copy the data** then runs as a background service on the server, step by step on screen: it makes the database if it is missing, makes every table that is missing and keeps every table that is already there, and copies every row the new server does not have yet. A row that is already there is left alone, a row that cannot be saved (for example a duplicate name) is skipped and listed with its reason, and the copy carries on; it can be run again safely, and adds nothing twice. Nothing is deleted or changed on the server the app uses now. Voice notes, pictures and documents are files in the storage folder, not database rows, so they stay where they are. **Use this server from now on** (it asks first) saves the choice, protected with the same key as the saved AI keys, in `App_Data/database.override` next to the app, and the app uses the new server from its next start (behind IIS it restarts by itself; elsewhere stop and start it). If the saved server cannot be reached at start-up the app still starts, on the server it was installed with, and the page shows why; **Go back to the server the app was installed with** removes the saved choice. The password is used for the test and the copy only and is never shown again. Changing the signing key (`Security:JwtSigningKey`) makes the saved choice unreadable, so the app then uses the server it was installed with.

A "user" is the server's `ImplementationLead` role (project lead of the projects they make). Nobody signs themselves up: the administrator adds people in **Users** and gives them the email and password shown once. An administrator cannot stop their own access or remove their own administrator role, so the system always has one.

The server also still has the finer roles of the earlier design (executive, reviewer, department assignments, confirmation, the Word requirement document). The app does not show them; they are used through the API.

## 2. What a user does

1. **New project**: pick the client (if more than one) and type a name. **Delete project** (the bin on a project's card, or on the project page) is for the project's lead and the administrator, and asks first. A deleted project leaves every list and nobody can open it, its documents leave the library, and the totals on the admin page no longer count it. Nothing is erased: the rows stay in the database marked with `DeletedAt`, and the AI usage it caused stays in the usage totals (shown as "Removed project"), because those tokens were really spent. To bring one back, an administrator clears `DeletedAt` on its row in the `Projects` table. (The project code stays reserved.) One request is made with it (the first new requirement, NR-001, in a module called General).
   **Modules and requests (the folders).** The project page opens with the way the company files its work: a project has **modules** (Ward, Nurse station, Pharmacy...), and each module has **New requirements (NR)**, **Change requests (CR)** and **Bugs (BUG)**. A bug is a request like the other two: it takes the same notes (typed, spoken, photographed, attached files), pictures, analysis and implementation document, and it is numbered on its own (BUG-001, BUG-002), so the document is `IMPL-WARD-BUG-001`. Every request has its own notes, workflow diagram and implementation document, and a number inside its module and kind: NR-001, NR-002, CR-001. **Only the administrator creates modules** (Admin, **Modules**: add, rename, stop; the short code in document numbers is made from the name, `WARD`, and does not change when the module is renamed). The project lead then adds a module to a project (**Add a module**) by **picking it from that list**, without the ones the project already has and without stopped ones; a name cannot be typed, and the server refuses a typed name (`Modules are created by the administrator`) or a stopped module (`module_not_available`). If the list has nothing left to add, the form says to ask the administrator. Stopping a module only removes it from the list: projects that already have it keep it, with their requests and documents. Projects made before this keep any module that was typed then; anyone who may capture for the module adds a request, either from the top (**New request**: pick the module, the type NR / CR / BUG, and type the name) or with **New** beside NR, CR or Bugs inside a module (asking for the same name again in the same module opens the existing request and numbers nothing new). Picking a request opens it. **Edit a heading**: the pencil beside the request name (anybody who may capture for the module) and beside the project name (the project's lead) turns the heading into a box (Enter saves, Escape cancels). The new heading shows at once; if the server refuses (the module already has a request with that name, in any letters) the box opens again with the reason. A request keeps its number when it is renamed, and its document gets the new title (a PDF that was already made keeps the old title until it is made again). **Delete a request** with the bin on its row (anybody who may capture for the module; it asks first). A deleted NR or CR leaves the lists and the document library and cannot be opened, but nothing is erased: its notes, versions and documents stay in the database marked with `DeletedAt`, its name is freed (the stored name gets `[deleted 002 yyyymmddhhmmss]` added), and **its number is never used again** (the next new requirement after a deleted NR-002 is NR-003). A project whose requests were all deleted stays, with its folders, so a new one can be made. To bring a request back, an administrator clears `DeletedAt` and removes the `[deleted ...]` tag from its name. Requests that existed before numbering became NR and were numbered 1, 2, 3 in the order they were made.
2. **Add notes** on the project page, any mix of:
   - **Record voice**: record in the browser, pause, listen back, send. Up to 7 minutes per recording (record longer interviews in parts). The recording is converted to a small WAV in the browser and sent in pieces that resume after a bad connection. The AI turns it into text.
   - **Add photos**: photos of handwritten or printed notes (several at once). Large photos are shrunk to 2200 pixels first. The AI reads them into text.
   - **Attach files**: any mix and any number of photos, recordings (mp3, m4a, wav, ogg, webm, up to 7 minutes each) text files (.txt, .md, .csv), **Excel workbooks (.xlsx)** and **PDF files**, chosen together or dropped on the notes. An Excel workbook or a PDF is read on the server, with no AI (so no free tokens and no per-minute wait), and saved as a typed note that says which file it came from: every sheet of a workbook becomes lines of cells separated by " | " (dates shown as dates, empty rows left out, up to 3000 rows a sheet), and a PDF gives the text of its pages (up to 150). A PDF that is only a scan has no text, and says so: photograph the pages instead. An old `.xls` file cannot be read: save it as `.xlsx` in Excel first. Files up to 12 MB. Each becomes a note of its own kind, three at a time, in the order chosen; a file that cannot be used is named with the reason and the rest are still added. A text file longer than 200 thousand characters, a recording over 7 minutes and other kinds of file (Word, for example) are refused with a message. If the free AI's limit of 20 photos or recordings a minute is reached, the sender waits a minute and carries on. On the server, at most three photos or recordings are read by the AI at the same moment, so a big batch does not hit the free quota all at once.
   - **Type a note**: saved on the device first, then sent with retry, so it works with no signal.
   Input can be added in any number of rounds, at any time, before or after an analysis: the next analysis uses everything.
   Every note shows what happened to it; a note that could not be read says why and can be tried again, edited or removed. Spoken and photographed notes can have their text corrected.
   **In one step:** once there are notes, the card at the top of the project page offers **Analyse and make the document**. It waits until every photo and recording has been read, analyses, then makes the PDF, showing which of the three steps it is on. The steps below are the same thing done one at a time, which is useful to answer questions or edit between them.
3. **Analyse**: the AI structures all the notes, and asks the questions it could not settle. Answer them, then analyse again. If nothing was added, changed or answered since the current version was made, **Analyse again** says so instead of spending free tokens on the same result, and offers **Analyse anyway**.
4. **Workflow and implementation document**: the workflow diagram (full screen, PNG), the numbers found, and **Create the implementation document** (section 3). Updating it after changes adds a new version of the same document. A panel beside the work shows what is done and the one next thing to do, and how many AI tokens this project has used.
   **Pictures for the document.** Under the workflow, **Attach pictures** takes screenshots of screens and photos of forms (JPEG, PNG or WebP, up to 20 per request, 8 MB each; large ones are shrunk in the browser first). Each has a caption (the file name to start with) and can be tied to a step, moved earlier or later, or removed. They are printed in the implementation document with their caption: a picture tied to a step under that step, the others in an **Attached pictures** section. The AI does not read them, so they use no tokens. A reviewer sees them but cannot change them.
   **One big PDF and a PDF for each module.** Under **Modules and requests**, the panel **PDFs of the whole project and of each module** makes **one big PDF of the whole project** (a cover, a contents page that links to each request, then every analysed request as a chapter that starts on a new page, grouped by module) and **a smaller PDF for each module** (the same layout with only that module's requests). They are written from the same analysed workflows as a request's own document, so they use **no AI**; a request that has not been analysed is listed on the contents page as not included, and each row shows how many requests are analysed. Press **Make PDF**, and later **Update** to add a new version of the same document (the older versions stay). The project PDF is numbered IMPL-{project code}-FULL and a module's IMPL-{module}-MOD, and both appear in the library (marked Whole project PDF or Module PDF) for the people who can open the project. The whole-project PDF is for the project's lead, the colleagues on its client and administrators; a module's PDF for anyone who may work in that module. Each is also saved on the device like a request's document (below).

   **Choose what goes in a PDF.** Before any implementation PDF is made (a request's own document, the project's, or a module's) a window lists the **headings the PDF would have, each with what is under it** (for example "Functional requirements: 2 rules, 3 requirements"); a heading with nothing under it is not listed. Beside the headings the window shows **the document itself, exactly as it will print**: the cover and then each ticked heading, drawn from the very page markup the PDF is made from (the real tables, the flow diagram, the pictures, the document number, version and who prepared it), numbered 1, 2, 3 without gaps and changing at once as headings are ticked or unticked. **Show** beside a heading scrolls the document to it. **Rename a heading**: the pencil beside a heading lets the person give it their own wording (Enter saves, Escape or Cancel closes only that box and keeps the window; at most 120 letters; the arrow beside a renamed heading goes back to the standard one, and "Use the standard headings" resets all). The document on the right changes at once, the PDF is printed with the new wording (in a request's own PDF and in a project or module PDF, in every chapter), the numbers do not change, and the standard heading is still shown under it ("Standard heading: Purpose") so it is clear what was renamed. Only the renamed headings that are ticked are sent (`titles` in the request: section key to new heading); the server checks them (`unknown_section`, `heading_too_long`), keeps them with the job (`DocumentJobRuns.TitlesJson`, migration `AddGuideTitles`) and swaps the heading of each printed section. A renamed heading is remembered in the browser for that document, so the next PDF of it starts with the person's wording. On a phone the window has two tabs, Choose and See the document. For a project or module PDF the document shows each ticked request as a chapter (pictures and the flow drawing are left out of that preview to keep it quick; they are in the PDF). The page is shown in a frame that cannot run scripts. Everything starts ticked; untick what is not needed and press **Make the PDF** (or **Update the PDF**). Only the ticked headings are written, and they are numbered 1, 2, 3 without gaps; the cover is always printed. For the project's and a module's PDF the window also lists the analysed **requests** by module, so a request can be left out as well. At least one heading (and one request) must stay ticked. In the one-step button ("Analyse and make the document") the window appears after the analysis, so the headings shown are those of the analysed workflow; cancelling it makes no document and keeps the analysis. The choice is for that run only: the next run starts with everything ticked. Document control and the sign-off table can be left out of a request's own document; they do not exist in the chapters of a bigger PDF. Behind the window: `GET flows/{id}/guide-outline`, `projects/{id}/guide-outline` and `projects/{id}/modules/{moduleId}/guide-outline` list the headings; the three `POST …/guide` calls take an optional body `{ "sections": ["purpose", "stages"], "flowIds": [...] }` (nothing sent means everything; an unknown section or an empty choice is refused). The choice is kept with the job (`DocumentJobRuns.SectionsJson`, `FlowIdsJson`).

   **Roles, final documents and verification.** Two roles. The **administrator** (the implementation head) makes users and clients, assigns users to clients, and verifies documents; the administrator does **not** make documents and does **not** see working copies. A **user** works on the clients assigned to them: projects, notes, analysis and documents, and sees only the documents of their own clients. Every document version is in one of four stages: **Working copy**, **Final** (marked by its maker, waiting for the administrator), **Verified** or **Returned** (with the administrator's reason). A user marks the **latest** version of a document as final (a request's document, a module's PDF or the whole-project PDF) with **Mark as final** on the request page, in the PDFs panel or on the Documents page; they add an optional note, and can **Take back** the mark until the administrator decides. Only one version of a document waits at a time. A returned version stays returned: the user updates the document and marks the new version as final. The administrator's **Final documents** page (the Documents link) lists only final documents (the version that was marked): filter by client, by the person who made it final and by status (waiting, verified, returned), search, open the PDF, then **Verify** or **Return** (a reason is required); the counts above the list are filters too, and the menu shows how many are waiting. The administrator's **Who handles what** page lists every client with the users on it and every user with their clients, with projects started, requests and final documents (waiting, verified, returned) for each, a client nobody handles and a user on no client are listed too; filter by client or user, or switch between By client and By user. The administrator is sent back to the admin pages if they try to open a user's project or request. Server rules: for the administrator `GET library`, `documents/{id}`, a document's download and diagram, and the lists of a request's or project's documents return only final versions (opening a working copy is 403); `POST documents/{id}/versions/{n}/final` (note optional) and `DELETE …/final` are for people who can work on the document; `POST …/approve` is for the administrator and only for a final version; making documents, notes and analysis are refused to the administrator (403); `GET admin/handling` lists who handles what. Versions are marked in `DocumentVersions.FinalizedAt/FinalizedBy/FinalNote`.

   **Design system.** The look is one set of tokens and components, in `web/src/styles/`: `tokens.css` (every colour, size, radius, shadow and speed, with the light and dark themes), `base.css` (reset, type, focus), `layout.css` (the dark navigation rail, the top bar with breadcrumbs, the phone tab bar, page headers, grids), `components.css` (buttons, form controls, switches, badges, alerts, cards, tables, tabs, dialogs, toasts, loading and empty states) and `pages.css` (what belongs to one screen). `styles.css` only imports them in that order. A new screen uses the existing classes and tokens; it does not write its own colours or radii. On a computer the menu is a left rail with groups (narrowing to icons on a tablet); on a phone it is a bottom tab bar that scrolls sideways when there are many items (the administrator's). Fonts (Geist) are bundled; nothing is fetched from the internet.

   **A copy on your own device.** When an implementation document is made while the page is open, a copy of the PDF is also saved on the device in use: on a computer in the browser's Downloads folder, or in a folder chosen once with **Choose a folder** (Chrome and Edge; the browser asks to allow writing there, and falls back to Downloads if it no longer may), and on a phone in the Downloads of the phone. The **Download** button uses the same folder. It is on by default and can be turned off under the document (**Keep a copy on this computer/phone**; the choice is remembered in that browser). A page can only write to a folder the person chose, and cannot choose the folder on a phone, so these are the places that work. The server keeps its own copy as well, because colleagues read documents from the library.
5. **Documents**: the implementation documents of the projects you can open (your own and your clients'), searchable, with the diagram and the PDF.
6. **AI usage**: tokens used this month, with the change on last month, a bar for each day, what they were for, which projects, the latest calls, and (for the administrator) which people. A user sees only their own usage. Every AI call is recorded: analysis, the document, voice notes, photos and key tests. The numbers are what the AI reports for each call; the free tier's own limits (calls per minute and per day) are set by Google and shown in Google AI Studio. In demo mode the AI uses no tokens, so the page says so.

The detailed view of a workflow (every section as a form, versions, compare, roll back) is under **Review and edit** on the project page.

## 3. The implementation document

One PDF per workflow, numbered after its module, kind and number (`IMPL-WARD-CR-001`; in the General module the project code stands in for the module: `IMPL-ABCD-1234-NR-001`; documents made before requests were numbered keep their old `IMPL-ABCD-001` number). The cover and the document control table also say the module and the request (`CR-001 (Change Request)`), laid out like the company's requirement documents. A cover (AOSTA INDIA PRIVATE LIMITED, BACKBONE, the document ID, project, who prepared it, date and workflow version; it shows the company logo when `templates/logo.png` is supplied), then: purpose and scope, who is involved, the flow at a glance (the diagram on its own landscape page so it can be read), the flow explained stage by stage in plain words with each decision where it is made, where it touches the system (screens, menus and masters; existing BACKBONE areas affected; hand-offs to other departments and systems; reports), the rules the flow must follow, the requirements and how they will be accepted, and assumptions and open points to confirm with the department. It deliberately explains the flow and its touch points and is **not** a development plan: there are no phases, effort sizes, tables or API designs. Anything unknown is left out of the tables and turned into a question under open points, so the page never prints "To be confirmed". Each page has a running header with the document number and a page number. It is built as a web page and printed to PDF by the same Chrome or Edge that draws the diagrams, so it needs no Word template or LibreOffice.

**The diagram is drawn by the server itself** (`FlowDiagramBuilder`), not by the AI and not by a browser, so the screen, the PDF and the Word document always show the same picture and it always matches the steps. Top to bottom: a dark START box that says what starts the flow, numbered step boxes that say who does it and, in blue, **on which screen** (the touch point), diamonds for real questions with labelled Yes and No routes, dashed boxes for alternative ways, ways back to an earlier step drawn round the outside with a "↺", and END. A step that leads to several steps (a menu of choices) has a labelled route to each one; rows with more than four boxes are staggered so the picture stays narrow. Text is wrapped and never runs outside its box. In the PDF **the whole diagram is always on one page, and that page is an ordinary A4 portrait page like every other page of the document** (same size, margins, header and page number). The builder tries the picture two to six boxes wide and with one to three side-by-side columns (a tall flow is cut between two rows of boxes and continues in the next column, marked "continues in the next column"), and uses the combination that shows it largest. It is vector drawing, so a very large flow stays sharp when zoomed, and the page says so. The PNG (for download and Word) is made from the same picture the first time it is asked for.

**The sections** (numbered, each only when there is something to say) follow the layout of the company's own requirement gathering documents, then go into the flow in detail: document control (every version of the document, when, by whom, from which workflow version), purpose, scope, **functional requirements** (the rules the solution must follow, the checks on entered information, the requirement table with ID, description, category and priority, and how each is accepted), **user roles and responsibilities** (role, what they do, frequency, module, menu), **use case description** (primary actors, trigger, pre-conditions, post-conditions, priority, main scenario), the flow at a glance (the diagram), how it works stage by stage (with decisions, alternative ways and what goes wrong), **screens and what they hold** (each page of the flow with the fields the department named for it, its type, whether it is required and its default when known, and the step it belongs to), where it touches the system (screens, existing BACKBONE areas, hand-offs, reports), assumptions and open points, and approval and sign-off (prepared by, reviewed by, approved by, with room for name, role, signature and date). Columns nobody filled in are left out, and nothing is ever printed as "To be confirmed": what the department did not say becomes a question under open points.

**A list in the notes cannot be squashed into one step.** After an analysis the server looks for lists in the notes ("Name: what it is" lines, bullets, numbers: at least three items). If most of the listed items did not become a step or a screen of their own, the AI is asked once more, with the list and the missing items named, and told that separate pages must be separate steps (or, if they are only fields of one screen, to say so by leaving the structure as it is). If it still does not, the analysis is accepted with a warning on the project page. Never more than one extra call.

**Prompts are stored in the database and are immutable.** A change to a prompt is a new file version in the `prompts` folder (`common-rules.v2.md`, ...). On start-up the newest version becomes the active one and replaces the earlier versions that also came from the folder (never one an administrator added by hand); the old versions stay stored for the record. Editing an existing version's file changes nothing: the server only logs a warning.

**Using the free tokens without waste.** An analysis thinks **lightly** the first time (thinking is billed as output); only the corrective second attempt thinks at medium depth. The second attempt is made only when a list in the notes was squashed into one step or the answer broke the rules, and when it was only a missing step it is told in words and the first answer is **not** sent back (that used to cost thousands of tokens for nothing). Analysing again with nothing new is refused (above). Pictures are never read by the AI. Voice notes go to Groq (section 4) when a Groq key is saved, which keeps the Gemini allowance for the analysis and for photos. Each Gemini call logs its input and output tokens (numbers only), so it is visible which step spends what. If the bigger models are busy and a Lite model answers, the result can still be thinner, so read the document before sharing it.

To make the picture and the document clear, the analysis prompt now tells the AI to make **a separate step for every page, tab or option the notes list**, each with its own screen and fields, reached from the menu step by a labelled route (never one merged step, never a chain of "Did the user select X?" questions), to use decisions only for real conditions, to list the fields the notes name for each screen, to ask for what the notes leave open (at most 10 questions, naming the page), and to leave the diagram to the server (it writes only `flowchart TD`, which also saves tokens).

**It takes seconds, not minutes.** The document is written straight from the analysed workflow (`GuidePlanBuilder`): one stage per step, each decision shown where it is made, the roles and the screens from the steps themselves. There is **no second AI call**, so it costs no tokens and does not wait for the free AI. The diagram is plain SVG text made in milliseconds and printed straight into the PDF (sharp at any size, no browser start for it); the PNG for the "PNG picture" button is drawn the first time somebody asks for it. Measured on the test server with the demo AI: the first document about 4 s (it draws the diagram), an update about 2 s (the diagram is reused). Before this change it was 6 to 11 s with the demo AI and about 4 minutes with the real AI.
The administrator can switch on **Let the AI rewrite the document wording** (AI setup, section 3). Then one more AI call polishes the wording, which takes about a minute and is counted on the AI usage page as "Guide". If that call fails, the plain version is still made.

## 4. The free AI

The administrator opens **AI setup**, follows three steps (create a free key at Google AI Studio, paste it, press Save), and the page tests it. One key does everything: analysis, the guide, listening to voice notes and reading photos. The key is stored encrypted (derived from the server's signing key; changing that key means entering the AI key again) and is never sent back to a browser. The model is picked automatically from the newest free "Flash" model the key can use, or chosen from the key's own list. Other choices on the same page: Claude (needs a paid key on the server; text only) and Demo mode (a fixed example, for trying the app).

**Limits of each Gemini model (the real free limits).** Google's free tier limits **each model** on its own: requests a minute (RPM), tokens a minute (TPM) and requests a day (RPD); the Rate limit page in Google AI Studio shows them (for the project the app was set up with on 18 November 2026: Gemini 3.8 Flash and 3.6 Flash 5 a minute, 250,000 tokens a minute and **20 a day**; Gemini 3.5 Flash Lite 15, 250,000 and 500). Those three are preset and an administrator can change any of them, or empty a box for no limit, in AI setup, section 3. The app writes down **every request it sends to Google** (`AiAttempts`: the answers that worked with their tokens, and the ones that failed with why: busy, limited, daily limit, no answer), because Google counts the failed ones too, and **never sends to a model that is at a limit**: it uses the next model that has room, waits out a per-minute or tokens-a-minute limit (at most a minute), or, when every model has used its day, refuses at once with a message that names each model and when it renews (midnight Pacific time) and sends nothing. When Google itself answers "daily limit", the app believes it and stops using that model until the day renews, however few requests it counted itself (the same key may be used elsewhere). **Test the key** does not ask a model that has used its day (each question is one of its requests). Everybody sees what is left: a line on the project page ("Free AI left today: 41 requests"), a warning when 5 or fewer are left, and a banner when all are used; the administrator sees every model with meters on the AI usage page.

**Overall daily limits for each AI account.** Under **Overall daily limits** (AI setup, section 4, optional) the administrator can also set a total for each account (Gemini or Groq) that stops the app at the limit.

**(Older text:) Daily free limits: the app stops at the limit.** Under **Daily free limits** (AI setup, section 3) the administrator enters, for Gemini and for Groq, how many requests and how many tokens a day the free account allows (leave a box empty for no limit in the app). The app counts what each AI has really used since its own day began (Gemini: midnight Pacific time; Groq: midnight UTC), taken from the usage records, and **stops sending anything to an AI that is at a limit**: Gemini calls are refused at once with `ai_quota_reached` and a message that says how much was used and when it renews; starting an analysis says so immediately instead of queueing; a voice note goes to Gemini when Groq is at its limit and Gemini still has room. The numbers are counted from what this app sent, so use made outside the app is not included, and Gemini's real limits are per model, so the total here is a safety net across all models (take the numbers from Google AI Studio, Usage and limits, and the Groq Console, Limits). The administrator's **AI usage** page shows each AI's use today against its limit with a meter and "renews in", which AI is paused, and every AI and model with its own calls and tokens for the month.

**Groq for voice notes (optional, recommended).** Under **Voice notes** on the same page the administrator can add a free Groq key (console.groq.com/keys, it starts with `gsk_`). Voice notes are then turned into text by Groq's Whisper on Groq's own free allowance, and Gemini is kept for analysing the notes and reading photos. If Groq is busy, over its allowance or refuses, the same recording goes to Gemini, so a note is never lost; a silent recording is reported at once and not sent to a second AI. **Test the Groq key** only lists the models (it spends nothing). The page shows what Groq last reported is left of its free allowance (taken from its answers). Without a Groq key, or when Gemini is chosen for voice, Gemini does it as before. The key is stored encrypted like the Gemini key. Groq's free limits change: check them in the Groq console.

**Speed and privacy switches** (AI setup, section 3): **Allow photos and voice recordings** (on by default). When the administrator switches it off, the Record and Photos buttons are disabled with an explanation, the server refuses them (HTTP 422, `media_blocked`), and typed notes keep working. **Let the AI rewrite the document wording** is off by default (section 3).

**When Gemini is busy.** The free tier often answers 503 (overloaded), or hangs, and each model has its own load and quota. With the model on **Automatic**, the app keeps a short list of models the key can use, best first, with the best of each *generation* before more of the same one (sister models such as 3.8 and 3.5 share the same overloaded servers). Every attempt has a time limit (analysis 100 s, voice 150 s, photo 90 s, key test 30 s), and a busy, limited, hanging or retired (404) model is skipped at once for the next one, with no waiting. A model that just failed goes last for 2 to 15 minutes (30 for a used-up daily quota, 60 for a retired model) and gets a 25 s limit when it is tried again, so it can never cost a long wait. If nothing answers within 200 s the person is told plainly that Gemini is overloaded and nothing was lost. Extraction tasks ask the model to think briefly (the slow part of a call), and fall back to the model's default if it refuses that setting. If the administrator **names** a model, only that model is used (3 attempts). **Test the key** now asks every model on the list at the same moment and shows which answered and how fast, and what it learns is used by the next analysis. The usage page shows the model that really answered.

**Fair use of the shared free key.** Everything that starts an AI call (analysis, the document, a photo, a recording) is limited per signed-in person to 20 a minute (`RateLimit:AiPerMinute`), so one person pressing buttons in a loop cannot use up everybody's free quota; they are told to wait a minute. Each attempt the server makes to Gemini is logged with its duration, HTTP status and the provider's reason (for example `RESOURCE_EXHAUSTED (PerMinute)`), and never the key, the prompt or the answer, so a slow or throttled call can be told apart from a slow model.

**Privacy:** Google's free tier may allow what is sent to it to be used to improve Google's products (check their current terms). The app hides patient numbers, phone numbers and names in text before it is sent, but it cannot hide them inside a photo or a recording. The page says so.

## 5. How it is built

| Part | Choice |
|---|---|
| App | React + TypeScript, built with Vite, in the `web/` folder |
| Data | TanStack Query over the REST API in `docs/03-api-contract.md`; no other server |
| Look | Plain CSS design system in `web/src/styles/` (`tokens`, `base`, `layout`, `components`, `pages`): colour, type, spacing and motion are variables; light, dark and "follow the device" themes; a dark menu on the left (collapsible) and a tab bar at the bottom on a phone; Geist font bundled with the app (nothing is downloaded) |
| Offline | A service worker keeps the app files, so it opens with no signal. Typed notes are saved in the browser (IndexedDB "outbox") first and sent with retry. Voice, photos, analysis and documents need a connection |
| Saving speed | Typed notes, photos and requests save in about 0.1-0.2 s on the server. The slow part used to be the **first** Excel or PDF read after the server started (about 1.0 s and 1.4 s while the readers load; every later read takes under 30 ms), so when two files were attached right after a restart the save took 4.7 s. The server now does that work itself in the background at start (`WarmUpHostedService`: it reads a tiny workbook and a tiny PDF and runs the first database queries; it logs `Warm-up finished in ... ms`, writes nothing and never delays the start). A note that reaches the server also appears in the list at once, without waiting for the list to be fetched again. Reading a photo or a recording with the AI, and making a document, are separate steps that take longer and are not part of saving |
| Hosting | The API serves the built app from its `wwwroot` folder: **one address**, no CORS. Pages such as `/p/123` work from a shared link or after a reload |
| Security | Strict Content-Security-Policy, short-lived access token in memory, refresh token in the browser. Files (photos, recordings, documents) are fetched with the sign-in and shown from temporary addresses, never public links |

### Working faster in the app

Everything here runs in the browser on the data the app already had; **no server, database or sign-in rule was changed for it**.

| What | How it works |
|---|---|
| **Search and commands** | `Ctrl+K` (`Cmd+K` on a Mac), `/` or the Search button in the top bar. Finds pages, your projects, documents (by title or number), and for the administrator people and clients. Arrow keys and Enter; the projects opened last are offered first. Also runs actions: switch light/dark, collapse the menu, refresh all data, show the shortcuts. What is searched is only what the signed-in person may already see |
| **Shortcuts** | `?` lists them. `[` collapses or opens the menu. For users: `n` new project, then `g` followed by `h` projects, `d` documents, `t` AI usage. For the administrator: `g` followed by `h` overview, `d` final documents, `w` who handles what, `c` clients, `u` users, `a` AI setup, `t` AI usage. They do nothing while typing in a field or while a window is open |
| **The menu** | Collapses to icons (name shown on hover and keyboard focus); the choice is remembered. A "Skip to the content" link, breadcrumbs, and a short fade between pages (switched off when the device asks for less motion) |
| **Lists** | Projects (when there are five or more), users, clients, documents and the administrator's final documents have search, filters, sorting and paging. The last choices are remembered per person in this browser, a link such as `/documents?status=Final` can choose them, and **Clear filters** goes back. Users, clients, handling and final documents can be exported as CSV (opens in Excel; cells that look like formulas are neutralised); handling can be printed. The AI usage page's "Latest calls" is a full table: sort (Shift-click for a second column), choose columns, page size, CSV, print |
| **Pins and recents** | Pin a project on Home to keep it at the top; "Continue where you left off" lists the projects opened last |
| **Forms** | Required fields are marked, mistakes are shown beside the field as soon as it is left (empty name, wrong or already used email, a client name already used, password rules ticking off as they are met). A project name already used for the client is warned about but allowed. Enter submits; a form with something typed asks before it is closed or cancelled; closing the browser tab with a half-filled form asks too. The client last used in New project is chosen for you |
| **Several at once** | The administrator ticks final documents (or "Select all waiting") and verifies them together: a list to confirm, progress, and the ones that failed are named and stay ticked so they can be tried again. A document is returned one at a time because a reason is needed |
| **Details without leaving the list** | A side panel for a final document shows who marked it final, the notes and the history of its versions; the document number can be copied from the list |
| **Mark as final** | Shows an **Undo** in the message that follows |
| **Messages** | Appear for a few seconds, can carry an action (Undo), and the bell in the top bar keeps the messages of this visit |
| **Refresh** | Overview, final documents, documents, handling and AI usage have a Refresh button and say when the numbers were loaded; when a page cannot load, it says why and offers Try again |

**Screen sizes.** Checked in a real browser from 320 px (small phone) to 1920 px: below 761 px the menu becomes tabs at the bottom (scrolling sideways if there are many) and buttons wrap their text; from 761 to 1100 px the menu is icons only (name as a tooltip); wider, the full menu, which the person can collapse. `e2e/responsive.spec.ts` fails if any main page scrolls sideways or the menu gets a scrollbar at 7 sizes. Tooltips on the menu appear only when it shows icons alone.

What is remembered in the browser: only display choices (theme, collapsed menu, filters and sort, page size, chosen columns, pinned projects, projects opened last, last client). It is kept per person on that browser, holds no password, token or document text, and the app works without it. Clearing the browser's data forgets it.

Not done, on purpose: a layout the person can rearrange (nothing needs it), named saved filters (the last filter is remembered instead), paging on the server (lists are small enough to load whole), and a block on leaving the page through the app's own links with a half-filled form (the browser's own warning on closing the tab and the Cancel confirmation are used instead).

## 6. Run it

You need Node.js 22 or later (nodejs.org) to build the app, once.

```powershell
cd web
npm install
npm run build                 # writes src/FlowCapture.Api/wwwroot
cd ..
dotnet run --project src\FlowCapture.Api --urls http://localhost:5199     # then open http://localhost:5199
```

The first start creates the database and the administrator from `Seed:AdminEmail` and `Seed:AdminPassword` (in development: `admin@flowcapture.local` / `ChangeMe-Dev-12345`). In Visual Studio, press F5 on `FlowCapture.Api`: the first build runs `npm install` and `npm run build` for you. While working on the app, `cd web; npm run dev` runs it live at http://localhost:5173 and forwards `/api` to port 5199.

Demo users: `.\scripts\demo-setup.ps1` makes `asha@demo.local` and `ravi@demo.local` (password `Demo-Passw0rd-123`). To try everything without an AI key, start the API with `Ai__Provider=Demo`.

## 7. Sharing a link, installing, and the microphone

The link is the address where the API runs. Browsers insist on HTTPS for three things:

- **The microphone.** Recording works on `http://localhost` and on any `https://` address, but **not** on `http://192.168.1.20:5199`. On such an address the Record voice button explains this. Typing, photos and everything else still work.
- **Installing** ("Add to Home screen") and the offline service worker.
- A link only others can open must point at a machine they can reach.

Ways to get a shareable HTTPS link: **host it** (Azure App Service, a VM or Docker behind a reverse proxy with a certificate: `docs/06-deployment.md`), or for a short demo a tunnel such as Visual Studio Dev Tunnels (Debug > Dev Tunnels), Cloudflare Tunnel or ngrok. Anyone with a tunnel link can reach your machine while it is on, so use it only briefly and close it.

On the phone: open the link in Chrome (Android) or Safari (iPhone), then menu > **Install app** / **Add to Home screen**.

## 9. Known limits

- **Groq, the pictures, the folders and the one-page diagram have not been tried with a real Groq key or real hospital material.** Groq is covered by tests against a faked service; the folders, pictures and one-page diagram are covered by unit, integration and browser tests with the demo AI. Whisper's accuracy on Tamil or Hindi mixed with English is untested.
- **The AI usage page** shows Gemini by what the AI reports per call; Google does not report what is left of the free allowance, so only Groq's remaining allowance is shown.
- **The free Gemini AI:** a real analysis and a real voice note have been tried by the owner with a real key and worked. Reading photos of handwriting with the real AI, and the optional AI document wording, have not been tried for real; they are covered by tests against a faked service. Real analyses took from 38 s to 275 s and two were refused by the free limit; the per-attempt log (above) is there to find out why. Model names and free limits change; the app lists what the key can use rather than assuming.
- Free limits apply (requests per minute and per day). When they are reached, the app says so and the action can be tried again later.
- A voice note is at most 7 minutes. Thick accents, code-mixed Tamil/Hindi/English and noisy rooms are the likely weak spot of any speech recognition; the text can be corrected before analysing.
- Offline covers opening the app and typing notes. Voice, photos and everything else need a connection. A typed note waits in this browser only: clearing the browser's data loses one that was never sent. Sign-out warns about waiting notes.
- Not tried: Safari, Firefox and a real phone. Everything was checked in desktop Chrome, at desktop and phone size, with a fake microphone.
- The PDF is made by Chrome or Edge on the server, so the server needs one installed (the Docker image has Chromium).
